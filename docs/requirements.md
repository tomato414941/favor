# 基本仕様（草案）

`commission` の取引を実装するための仕様草案。基準日は2026-09-13。
アプリ、決済連携、本番環境は未実装であり、本書は公開用の利用規約ではない。

## 1. 方針と記述の区別

- **合意済み**：基本モデルはSkeb準拠。リテイク要求・見積もり・打ち合わせを設けず、作り手の裁量を尊重する。対象ジャンルを独自に絞らない。
- **確認済みの基準**：公式ガイドに記載された利用者向けの挙動。Skebの内部実装を確認したものではない。
- **設計案**：その挙動を実現するための状態、データ、整合性の扱い。
- **未確定**：情報や判断が不足している点。仮の値や独自ルールで埋めない。

実装は基本取引から順に進める。これは、後述の関連機能を製品の対象から除外する決定ではない。
企画全体と名称候補は[README](../README.md)を参照する。

## 2. 確認済みの取引基準

以下は[クライアントガイド][skeb-client]と[クリエイターガイド][skeb-creator]から確認した主要条件の要約。全規約・全画面の照合は未完了。

| 項目 | 基準となる挙動 |
| --- | --- |
| 依頼 | 本文で内容を完結させ、依頼者が金額を提示する。作り手は受けるものを選ぶ。 |
| 金額設定 | 作り手の設定は推奨額と最低額。独自料金表や追加ルールは設けない。 |
| 支払い | 送信時にカード与信またはポイントを確保し、承認時に決済する。 |
| 期限 | 承認・納品とも送信日を起点とする。承認を遅らせても納品期限は延びない。 |
| 承認前の取消 | 作り手の辞退、依頼者の取消、返答期限切れを扱う。 |
| 承認後の未納品 | 期限超過や作り手のギブアップによる取消を扱い、支払いを戻す。 |
| 納品後の修正 | 依頼者のリテイク要求は禁止。作り手自身による期限内の再納品は可能。 |
| 公開と匿名 | 公開・匿名・非表示を区別する。匿名では作り手にも依頼者を明かさず、金額は第三者に公開しない。 |
| 非表示と権利 | 非表示はサービス内の掲載設定であり、秘密保持や権利譲渡ではない。 |
| 返金先 | カードとポイントで処理が異なる。依頼のポイント返還と、ポイント購入自体の返金は区別する。 |

カードへの返金反映は即時とは限らない。取消の成立と支払い側の処理完了を同一視しない。[返金の基準][skeb-client]

## 3. 基本取引の状態案

この節以降の状態名・データ構成は、このプロジェクトの設計案である。

### 3.1 依頼の状態

| 状態 | 入る条件 | 次の遷移・制約 |
| --- | --- | --- |
| 下書き | 依頼内容を入力している | 支払確保を確認し、送信が成立したら承認待ち。支払確認中・失敗時は作り手に送信済みと表示しない。 |
| 承認待ち | 内容・金額・相手・期限を確定し、支払確保を確認した | 承認処理中、またはキャンセルへ。 |
| 承認処理中 | 作り手が承認し、重複操作を排除して請求確定を要求した | 請求成功を確認して制作中へ。結果不明のまま制作開始を案内しない。 |
| 制作中 | 請求確定が成功した | 有効な納品で納品済みへ。未納品のまま期限超過・ギブアップならキャンセルへ。 |
| 納品済み | 納品物の保存・必要な検査・閲覧権限設定が完了した | 依頼者による検収承認を追加しない。作り手の期限内再納品でも元の期限は変えない。 |
| キャンセル | 辞退、取消、期限超過などが成立した | 支払状態に応じて確保解除または返金を進める。依頼を自動で復活させない。 |

承認処理で失敗した場合、支払確保が有効で期限内なら再試行の可否を判定する。期限切れや確保失効ならキャンセルへ進める。
通信エラーだけで請求失敗と断定せず、決済事業者側の結果が分かるまで処理中として照合する。
失効と請求成功が競合した場合も、作り手への制作開始通知を出す前に結果を確定する。

### 3.2 支払いの状態

依頼の状態とは別に、次の状態と外部処理の識別子を管理する。

- 未確認／確保処理中／確保済み。
- 請求処理中／請求済み。
- 解除処理中／解除済み。
- 返金処理中／返金済み。
- 要照合：外部処理の結果が不明、または状態に不整合がある。

要照合の場合も、直前に確認できた金額・状態と、結果を待っている操作を保持する。
カード与信の解除と、請求後の返金を使い分ける。ポイントを扱う場合も、ロック解除と残高への返還を区別する。
返金の失敗・遅延があっても返金義務の記録を失わず、再試行・運営確認の対象として残す。
売上の計上と作り手への出金も別処理とし、依頼の請求成功を出金完了として扱わない。

### 3.3 時間と競合の扱い

- 送信成立時刻、承認期限、納品期限を依頼ごとに保存する。作り手が後で設定を変更しても既存依頼の期限を変えない。
- 承認・取消・納品はサーバー側で状態と期限を検証する。画面上のボタン表示だけに依存しない。
- 送信・依頼者側の取消は本人、承認・辞退・納品は対象の作り手の権限で検証する。運営の例外操作は別権限と監査記録を必要とする。
- 承認と取消が競合したら、二つの処理を同時に成立させない。
- 決済要求と通知は重複を想定し、同じ操作で二度請求・返金・売上計上しない。
- 遅れて届いた決済通知によって、キャンセル済みの依頼を制作中に戻さない。請求が成立していれば返金を含む整合処理を行う。
- リダイレクト先の表示やブラウザーの申告だけで支払成功を確定しない。

日数の初期値・設定可能範囲・タイムゾーン・日付境界・締切ちょうどの扱いは、追加照合が必要。Skebと同じだと推測して固定値を入れない。

## 4. 保持する情報の案

| 対象 | 主な情報 |
| --- | --- |
| 利用者と権限 | 利用者ID、認証先、利用制限、作り手としての受付状態。匿名表示と内部の本人識別は分ける。 |
| 作り手の設定 | ジャンル別受付、推奨額・最低額、返答・納品期限の設定。 |
| 依頼 | 当事者ID、ジャンル、本文、金額・通貨、公開設定、閲覧注意設定、送信時刻、期限、状態、取消理由の内部分類。 |
| 支払い | 支払方法、外部取引ID、確保額、確保期限、請求・返金の額と状態、重複処理を防ぐ識別子。 |
| 納品 | 依頼ID、版、ファイル情報、保存先、検査状態、納品成立時刻、公開用データと原本への権限。 |
| 売上と出金 | 適用手数料と条件の記録、計上・取消履歴、出金処理と照合状態。 |
| 操作記録 | 操作者、操作対象、変更前後の状態、時刻、外部通知ID。決済情報などを必要以上にログへ残さない。 |

これは論理的な整理であり、データベースや技術スタックの採用決定ではない。
金額は通貨に応じた最小単位の整数で扱い、手数料の丸め方は仕様として別途確定する。
カード番号・セキュリティコードをアプリのデータやログに保存する設計にはしない。

## 5. 未登録クリエイターへの入口

未登録の相手への依頼は、基本取引に対する**追加検討案**。まだ採用済みではない。
招待の受信先、本人の登録・確認、正式依頼の宛先を区別する。相手を指すURLを知っているだけでは本人確認とみなさない。

検討する流れは、内容と金額の入力 → 金額分の与信確保 → 招待 → 本人確認・登録 → 正式依頼への移行。
正式依頼への移行だけでは請求確定せず、作り手の承認と有効な支払確保を必要とする。

以下は未確定のまま基本取引へ混ぜない。

1. 招待の指定方法と配送方法。ファンがリンクを渡す方式か、運営が配送する方式か。
2. 招待から正式依頼へ移行する条件と、依頼者による再確認の要否。
3. 招待・与信・正式依頼の三つの期限と、正式な送信時刻の起点。
4. 当初の与信を利用できる条件、失効時の解除、新たな支払確認。自動更新や二重与信を前提にしない。
5. 送信数・保留数・同一相手への再送制限と、登録不要の受信拒否。

カード登録だけを金銭拘束とはみなさない。与信確保も送信ごとに失う費用ではないため、それだけでスパムが防げるとは扱わない。
返金しない送信料は採用していない。

与信には支払方法・条件ごとの有効期限がある。例として、[Stripeの公式資料][stripe-hold]では、期限内の請求確定が必要とされている。
実装時は実際の有効期限を確認し、返答期限と両立できなければ決済設計を再検討する。返答期限の短縮が必要になる場合は、Skeb準拠からの差分として判断する。
この参照は、Stripeの採用や、この取引方式への利用承認を意味しない。

## 6. 実装時の検証項目

以下は**テスト計画**であり、実装済み・テスト成功という意味ではない。

1. 支払確保に失敗した依頼が、送信済みや承認待ちにならない。
2. 送信・承認を連打しても、依頼や請求が重複しない。
3. 承認が遅れても納品期限が延びない。締切前後と同時刻の境界を、確定した期限仕様に従って検証する。
4. 依頼者の取消と作り手の承認が競合しても、一方だけが成立する。
5. 承認処理中の通信切断で、請求済みの依頼を未払いと誤認しない。
6. 与信失効後に承認できず、解除状況を追跡できる。
7. 未承認の失効では確保解除、請求後の未納品では返金を行い、処理途中を完了表示しない。
8. 決済通知が重複・逆順・遅延しても、二重処理やキャンセル済み依頼の復活が起きない。
9. 未承認の依頼や、期限切れの依頼を納品済みにできない。アップロード開始だけでは納品成立としない。
10. 作り手の期限内再納品で、元の納品期限や売上を重複更新しない。依頼者のリテイク要求機能は設けない。
11. 対象の作り手以外は承認・辞退・納品できない。匿名依頼の依頼者情報は作り手向けAPI・通知・表示から漏らさず、金額は第三者へ公開しない。
12. 非表示作品が公開一覧・検索・公開APIに出ず、原本が第三者向けURLから取得できない。
13. 返金・出金が失敗した場合、状態と履歴が残り、重複実行を避けて復旧できる。
14. 招待の未採用・失効・本人未確認の状態から、自動で正式依頼や請求が成立しない。

## 7. 残る照合と実装の順序

### 照合を続ける項目

| 領域 | 次の確認 |
| --- | --- |
| 入力・ファイル | 文字数、金額範囲、期限の設定値、全ジャンルの形式・容量・件数、納品成立と検査の順序。 |
| 手数料 | リクエスト・ブースト・出金それぞれの条件、割引判定時点、丸め。SNS掲載による割引など、サービス固有条件の置き換え。 |
| 決済・本人確認 | 対応事業者と取引方式の審査、与信期限、カード・ポイント、作り手の本人確認、返金・出金・不正利用時の扱い。 |
| 公開・権利・運営 | 利用範囲、閲覧注意設定、作品検査、違反・通報・凍結、データ保存・削除、問い合わせ対応。 |
| 関連機能 | ブースト、マルチポスト、再送要請、アピール、金額の自動調整、自動翻訳、SNS連携、印刷関連。対象から除外せず、個別に仕様化する。 |

公式ガイド上の条件と、この運営主体が契約・実装できる条件は別に確認する。
外部提携や決済サービスを、Skebと同じ条件で利用できると仮定しない。

### 実装の順序案

1. 技術スタックを決め、外部通信と実際のお金の移動を伴わない、基本取引の状態遷移と自動テストを作る。
2. 保存処理・権限・期限処理と、決済の模擬実装を接続する。
3. 依頼送信・承認・納品・履歴の画面を作り、利用者に表示される文言を確認する。
4. 契約・運用条件を確認した上で決済のテスト環境を接続し、照合・復旧・運営手順を検証する。
5. 関連機能を照合・実装する。未登録クリエイターへの入口は、採否と未確定事項を解消してから組み込む。

この順序は作業を分けるための案であり、途中段階をSkeb同等の完成品として公開する計画ではない。
