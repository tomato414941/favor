# commission

ファンが好きなクリエイターに作品の制作を依頼するサービス。
この文脈での **commission** は、報酬を伴う作品の制作依頼を意味する。

## プロジェクト

- プロジェクト名は `commission`。正式なサービス名ではない。
- 会員向け投稿・コメント・DMを中心とする既存の `fan-site` とは別プロジェクトとして扱う。

## 仕様資料

- [基本仕様](docs/requirements.md)：基本ルール、取引の流れ、未決定事項。

## 構成・起動

- 画面：React + Vite + TypeScript。サーバー：Node.js + Fastify。DB：SQLite（`node:sqlite`）。
- Node.js 24.14以上・25未満を使用する。SQLiteと納品ファイルは `data/commission.sqlite` に保存する。
- ローカル体験用として、依頼者・作り手の切替と模擬決済を使う。実際のカード請求・ポイント購入・出金は行わず、サーバーは `127.0.0.1` だけで待ち受ける。

```sh
npm ci
npm run dev
```

画面は <http://127.0.0.1:3211>。体験用設定は承認7日・納品30日、本文2,000文字、納品24ファイル・合計8 MB。正式な提供条件とは区別する。
`npm run build && npm start` では <http://127.0.0.1:3210> で起動する。

検証は `npm run check`。ブラウザー検証は Python 3・Playwright・Chromiumを用意し、`npm run test:browser` を実行する（専用の一時DBを使用）。

### 招待を試す

1. 「招待を送る」で、体験用の宛先 `@mio_demo` または `@sora_demo` と依頼内容を入力する。
2. 作成された招待リンクを、別のブラウザープロファイルやプライベートウィンドウで開く。
3. 宛先に対応する体験用アカウントで確認する。相手と異なるアカウントでは、本文・金額の閲覧も受諾・辞退もできない。
4. ルールに同意して登録・受諾し、「依頼一覧へ」から納品する。辞退や受信停止だけなら登録されない。

リンクの再発行・取消も可能。同じ相手への新しい招待は24時間に1件までという体験用制限を設けている。
実SNSへのログイン・アカウント検索はまだ接続しておらず、画面の「SNSアカウント」は固定の体験用データ。
招待受諾時のアカウント作成・永続セッション・取引への移行は実装済みだが、一般向けの登録・ログインや本番運用ができる状態ではない。

## 決定事項

1. 取引の基本モデルと主要ルールは、Skebを基準にする。
2. 依頼者によるリテイク要求は禁止する。見積もり・打ち合わせ・依頼に関する自由なやり取りを前提にしない。
3. 作り手は受けたい依頼を選び、表現や仕上がりに裁量を持つ。
4. ジャンルによる分類や選択は設けず、希望する内容は依頼本文に記載する。
5. 作り手ごとの独自料金表・追加ルールなどを、独自仕様として追加しない。
6. 正式名称の決定は保留する。

手数料、期限、決済・返金、権利、公開範囲、対応形式などは、公式資料との照合事項として扱う。
既存の `fan-site` の会員課金や手数料設定は引き継がない。

基準資料： [Skebクライアントガイドライン](https://lp.skeb.jp/client)、[Skebクリエイターガイドライン](https://lp.skeb.jp/creator)。

## 未登録クリエイターへの招待

ファンから招待リンクを共有し、作り手が受けるときに登録する入口を採用する。
これはSkeb準拠の取引モデルに対する追加機能で、現在はローカル体験版で実装している。
「依頼者の登録を不要にする」という案とは区別する。

### 宛先・共有・権限

- 本番ではSNS上の宛先をサーバー側で検索し、変更可能な表示名・ユーザー名ではなく、SNSの提供元と固有アカウントIDに結び付ける。体験版は固定の対応表を使う。
- 作成したリンクは依頼者が、相手が連絡を受け付けているDMやメールで共有する。自動DM・自動投稿・一括通知はしない。作成だけで「相手に届いた」とは扱わない。
- リンクだけでは本文・金額・依頼者名を返さない。認証された宛先アカウントとの一致を、閲覧・受諾・辞退の各APIで確認する。
- SNS側の認証結果を信頼する。SNS自体の乗っ取り防止やアカウント復旧は、このサービスの実装範囲には含めない。
- サービス内で匿名を選んでも、依頼者自身のSNSから共有すれば相手にアカウントが伝わる。
- 招待URLは256ビットの乱数をフラグメント部分に持ち、APIには専用ヘッダーで渡す。DBにはハッシュのみを保存する。HTML・共有プレビューは一般的な案内だけにする。
- 再発行は古いリンクを即時無効化する。取消・期限切れではリンクからの閲覧も終了する。いずれも元の期限は延ばさない。
- 生のリンクは作成・再発行時のみ返す。応答が失われても同じ操作キーで招待や与信を重複作成せず、必要なら明示的にリンクを再発行する。

### 登録・支払い・期限

- 招待は通常の依頼と別に保存する。SNSアカウントの確認だけではサービスのユーザー登録や請求確定を行わない。
- リンク作成時に提示金額全額のカード利用枠を確保する。招待の受諾期限は、承認期限・与信の有効期限・納品期限のうち最も早い時点まで。
- ルールへの同意・登録・受諾で通常の依頼に移し、その与信を引き継いで請求を確定する。登録・移行の途中で失敗した場合は元に戻す。
- 支払確認中は制作・納品に進めない。期限後の決済通知でキャンセル済みの依頼を復活させない。
- 承認・納品期限の起点は招待リンクの作成日時。手動で共有した日時は追跡せず、登録・受諾によって期限をリセットしない。
- 辞退・取消・無反応による期限切れでは確保を解除する。与信を無期限に維持したり、自動で取り直したりしない。
- 招待は現時点ではカードのみ。体験版の確保・請求・解除・返金は模擬処理であり、実際の決済事業者への接続はない。

与信確保は一時的な金銭拘束であり、送信ごとに費用を失う仕組みではない。
単独でスパムを防げるとは考えず、次の制限を組み合わせる。数値は体験用であり、正式な提供条件は未決定。

- 依頼者ごとに未受諾5件・直近24時間の作成10件まで。
- 同じ宛先の未受諾招待の重複を禁止。辞退・取消後も作成から24時間は新しい招待を作れない。
- 同じ招待のリンク再発行は1時間に5回まで。
- 受信者は宛先アカウントを確認したうえで、登録せずに今後の招待を停止・再開できる。停止時は未受諾の招待を見送り、確保を解除する。

返金しない送信料は採用していない。

参考： [Stripeの与信確保と請求確定の分離](https://docs.stripe.com/payments/place-a-hold-on-a-payment-method)。
与信の期限や対応条件は支払方法などで異なる。この資料を参照していることは、Stripeの採用や、想定する取引方式の利用承認を意味しない。

## 未決定事項

1. 最初に対応するSNSと、公式認証・宛先検索の接続設定と実装。
2. 一般利用者の登録・ログイン、募集設定、利用同意の正式な内容。
3. 想定する取引を扱える決済事業者と、本人確認・請求・返金・出金の実現条件。
4. 招待・送信制限・再送制限の正式な数値と、不正アカウント・決済手段への対策。
5. Skeb準拠で転記すべき条件と、追加案によって差分が生じる箇所。
6. 最初の利用者をどう集め、運営・問い合わせ対応をどう担うか。

体験用認証は `buildApp` の `demoAuth: true` で明示的に有効にする。無効時は切替APIを登録せず、保存済みの体験用セッションも拒否する。
これは本番モードの実装を意味しない。起動は引き続き `--demo`・ローカル待受のみ。

## 名称候補（保留）

名前の軸は「作り手に任せる」。以下は検討候補であり、採用や利用可能性を確認した名称ではない。

| 候補 | 意図するニュアンス |
| --- | --- |
| omakase | 作り手の腕や感性を信頼して任せる |
| Your Call | 判断・決定を作り手に委ねる |
| Surprise Me | 意外性や完成品を受け取る楽しみを期待する |
| Up to You | 作り手の自由な選択を尊重する |

公開名を決める前に、既存名称との混同、商標、ドメインなどを確認する。
